# Advertencias de las revisiones nativas (U02-U04)

Hallazgos no bloqueantes de las revisiones de Gentle AI, en su texto original. La unidad H1 decide cuáles se corrigen; cada uno queda marcado con su resolución en `decisions.md`.


## U02 (approved)
- R4-manifest-concurrent-write (WARNING, 01-OilGas-Production-Forecast/src/oilgas/ingest.py:134-164): _write_manifest, append_manifest and mark_manifest all perform an unlocked read-modify-write cycle (read_manifest -> mutate list -> _write_manifest) and every call to _write_manifest reuses the same fixed temporary filename '<manifest>.tmp' rather than a per-process unique name. Two overlapping invocations against the same manifest.json (for example an Airflow retry overlapping a manual rerun, or a backfill task running alongside the scheduled run) can interleave writes to that shared temp path or have one process's read-modify-write clobber the other's update, corrupting or silently dropping manifest entries and defeating the run_key idempotency guarantee (RNF05 in docs/decisions.md) that retries are supposed to rely on.
- R4-status-downgrade-on-replay (WARNING, 01-OilGas-Production-Forecast/src/oilgas/ingest.py:147-155): append_manifest replaces any existing entry for a run_key unconditionally, with no check on the entry's current status. If the download step for a run_key is re-executed after the pipeline already marked that run 'loaded' (operator reruns just the download task, or an orchestrator replay of a cleared task), the manifest entry for that run_key is silently downgraded from status='loaded' back to status='downloaded'. last_loaded() then stops returning that run (it only scans for status=='loaded'), so the next is_changed() check reports a false 'changed' even though the warehouse already holds the data for that run, with no error raised anywhere -- a path to a duplicate load into pipeline_runs.source_* on a subsequent pipeline execution.
- R4-no-observability-logging (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/ingest.py:71-212): None of _open, head_remote, download_file, append_manifest or mark_manifest emit any log record -- there is no logging import or call anywhere in the 257-line module. Operational visibility into download progress, size-mismatch truncation, connection resets, or silent run_key replacement in the manifest depends entirely on exceptions propagating up to the orchestrator; a stalled or truncated GET, or a run_key replacement that quietly overwrites an existing entry, leaves no trace in production logs besides whatever the caller happens to print on the final exception.
- R3-user-agent-unasserted (WARNING, 01-OilGas-Production-Forecast/tests/unit/test_ingest.py:234-235): decisions.md D24 commits to a precise `User-Agent: oilgas-pipeline/0.1` header and to never sending `Range` or conditional headers, and the fixture records every request's headers, but no test asserts the User-Agent value or the absence of If-None-Match/If-Modified-Since; only the absence of Range is checked. The documented contract for these headers is left unproved by any externally observable assertion.
- R3-download-http-error-unasserted (WARNING, 01-OilGas-Production-Forecast/tests/unit/test_ingest.py:272-276): decisions.md D24 states that any non-404 HTTP error is propagated as-is so the orchestrator can retry. This is verified for `head_remote` (test_head_other_http_errors_propagate, lines 80-84) but there is no equivalent test for `download_file` receiving a non-404 HTTP error (e.g. a 500 on GET), leaving that half of the documented retry contract unproved for the download path specifically.
- R3-quarantine-cross-device-untested (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/ingest.py:251-256): `quarantine()`'s cross-device fallback branch (os.replace raising OSError, then unlinking an existing target and using shutil.move) has no test exercising it; both quarantine tests operate within a single filesystem so this branch, including its unlink-before-move idempotency handling, is unproved.
- R3-unbounded-write-before-size-check (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/ingest.py:196-210): download_file streams and writes every byte the server sends until EOF before comparing `received` to the announced size; if a server ever returns substantially more data than announced, all of it is written to `<dest>.part` before the mismatch is detected and DownloadError is raised. This is consistent with the documented 'compare after the fact' design and is not demonstrated as reachable against the real publication server, so it is a hardening note rather than a proven defect.

## U03 (approved)
- R2-v04-dead-value-column (WARNING, 01-OilGas-Production-Forecast/src/oilgas/validate.py:258-260): V04's example frame is built with a 'value': pk column that is computed but never surfaced, because the output mapping passed to _examples only requests 'well_id' and 'period_key'. This is dead/copy-paste residue (compare V05 at lines 270-272, which does use its 'value' column) that invites a future maintainer to believe V04 examples carry a meaningful 'value' field, or to 'fix' the mapping and accidentally change the report's JSON/Markdown shape.
- R2-v16-missing-vs-outside (WARNING, 01-OilGas-Production-Forecast/src/oilgas/validate.py:342-345): decisions.md D25 states that V16 'incluye coordenadas ausentes como «fuera de la cuenca»' (treats missing coordinates as 'outside the basin'), but the code assigns a distinct reason label 'missing' that overrides the 'outside' default for those rows. The counting is identical either way, but the documented behavior and the emitted example 'reason' field disagree, which can mislead a maintainer who trusts the decision log when reading or extending V16's examples/consumers.
- R2-v20-duplicated-period-index-formula (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/validate.py:404-405): _rule_v20 re-derives a period index from period_key via `(joined.index // 100) * 12 + joined.index % 100 - 1` instead of reusing the `year*12+month-1` logic that produces `pidx` earlier in validate_file (line 253). The duplicated, uncommented arithmetic hides the fact that 'age' is in months and ties the rule to the exact period_key encoding (YYYYMM); a future change to that encoding would silently desynchronize this formula from the rest of the module.
- R2-typed-subset-unused-source (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/validate.py:423): _typed_subset iterates `for source, (english, kind) in USED_COLUMNS.items()` but never uses `source`; the dangling loop variable obscures whether the Spanish source-column name is supposed to matter here, and a reader has to check the whole function body to confirm it is unused.
- R2-validate-file-monolith (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/validate.py:184-381): validate_file is one ~200-line function evaluating all 20 V-rules and 3 I-rules through side-effecting closures (`add`, `row_rule`) that mutate a shared `results` dict rather than returning values; whether a rule was registered is only checked implicitly against the `RULES` dict order at `finish()` time. Adding a new rule and forgetting to call `add` for it produces no error, just a silent entry in `not_evaluated`, making the control flow easy to get subtly wrong when extending the module.
- R3-v01-parser-error-untested (WARNING, 01-OilGas-Production-Forecast/src/oilgas/validate.py:213-217): decisions.md explicitly states V01 must also reject CSVs that cannot be parsed structurally (its own example is a file with unclosed quotes), and the code does catch pd.errors.ParserError for this. But no fixture or test in test_validate.py / test_validate_rules.py exercises a structurally malformed CSV (only `not_utf8` for decoding and an empty file for EmptyDataError are covered). The ParserError branch of V01 is therefore shipped with zero externally observable proof that it behaves as the decision log claims.
- R3-validationerror-dead (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/validate.py:119-121): ValidationError is introduced and documented as 'the file was rejected: at least one blocking rule failed', but nothing in validate.py ever raises it; rejection is communicated only by returning (report, None). The only test that references it (test_validation_error_is_a_runtime_error) checks its class hierarchy, not that any code path raises it. The exception's described behavior is therefore unproven and effectively dead inside this module.
- R3-i01-nan-conflation (WARNING, 01-OilGas-Production-Forecast/src/oilgas/validate.py:365): I01 ('meses sin producción con estado de extracción efectiva') is computed as `(well_status == EFFECTIVE_STATE) & ~producing & ok`, where `producing = (oil > 0) | (gas > 0)` from line 316. When oil_m3/gas_thousand_m3 are unparseable text (already flagged separately by V07), `_float` yields NaN, and pandas numeric comparisons with NaN evaluate to False, so `producing` is False and such rows are counted as 'no production' even though production is actually unknown/corrupted, not zero. No test distinguishes a genuinely-zero-volume idle row from an unparseable-volume row for I01, so this conflation is unproven and could silently inflate the informational count on rows that are really a data-quality problem.

## U04 (approved after correction 589a497)
- R4-busy-timeout (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/warehouse.py:195): load_validated_subset acquires the write lock with a bare `BEGIN IMMEDIATE` and the connection returned by connect() sets only journal_mode/synchronous/foreign_keys pragmas, with no busy_timeout override and no retry/backoff around the lock acquisition. If a second pipeline invocation (manual rerun overlapping a scheduled one, or a model job writing model_* tables concurrently) tries to load while another load is mid-transaction, the call fails immediately with sqlite3.OperationalError('database is locked') instead of degrading gracefully (e.g. bounded retry), aborting the run on what is a plausible operational race rather than a true data problem.
- R4-schema-drift (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/warehouse.py:125-128): apply_schema only runs CREATE TABLE IF NOT EXISTS from sql/schema/*.sql with no migration step. If a future edit to 001_core.sql or 002_model.sql adds or renames a column on an already-materialized warehouse file, apply_schema will silently skip re-creating that table, and the later raw_monthly_production insert (built from `columns = ", ".join(frame.columns)` against the pre-existing table shape) will fail with a generic sqlite3 error that gives the operator no direct signal that the root cause is schema drift rather than bad input data.
- R4-check-sample-size (SUGGESTION, 01-OilGas-Production-Forecast/src/oilgas/warehouse.py:67): CheckFailedError's human-readable message truncates to the first 2 sample rows per failing check, and run_checks itself caps each check's stored sample at SAMPLE_LIMIT=5 rows. For an operator triaging a failed production load from logs alone (rather than catching the exception object and reading `exc.checks`), this gives a narrow view of how widespread a given control violation is, which matters for deciding whether a failure is a one-off bad row or a systemic data problem.
- R3-empty-frame-commit-then-crash (BLOCKER, 01-OilGas-Production-Forecast/src/oilgas/warehouse.py:216-224): load_validated_subset computes `MAX(period_key)` after the replace, then calls `int(last)` outside the try/except that guards the transaction. If the loaded frame ends up with zero rows in raw_monthly_production (e.g. an empty validated subset), MAX(period_key) is NULL, `conn.execute("COMMIT")` has already succeeded inside the try block, and the subsequent `int(last)` raises TypeError after the data-wiping commit is already durable. This directly contradicts the module's own documented contract ('the transaction is rolled back and the warehouse keeps exactly what it had' / docstring on lines 185-190) because the warehouse no longer keeps what it had, yet the function does not return a LoadResult and instead raises an unhandled exception to the caller.
- R3-fixed-attr-raw-coords (WARNING, 01-OilGas-Production-Forecast/sql/marts/production/dim_well.sql:25-31): The `attributes_changed` flag (surfaced as FIXED_ATTR_CHANGED) is computed from COUNT(DISTINCT lon), COUNT(DISTINCT lat) and COUNT(DISTINCT depth_m) over the *raw* (uncorrected) values across all of a well's rows. A well whose coordinates or depth were corrupted (swapped or out of range) in only some of its reported months — rather than consistently in every row — would show more than one distinct raw lon/lat/depth value purely because of the data-quality defect, and would therefore also be flagged FIXED_ATTR_CHANGED in addition to COORDS_SWAPPED/COORDS_OUTSIDE/DEPTH_INVALID. None of the new tests (test_dim_well_corrects_and_marks_coordinates_and_depth, test_outside_coordinates_become_null_and_the_last_province_is_kept) exercise a well where the coordinate/depth defect appears in only a subset of months, so this interaction between the quality corrections and the fixed-attribute check is unproved.
